# 0006 — The application is written in Rust

**Date**: 2026-08-30 · **Status**: accepted

## Context

A keyboard-first TUI and a single distributable Linux binary pointed at two
candidates, Go and Rust. Joel dismissed the learning-curve argument outright:
"if Rust is better, we take Rust, I'm the one who'll adapt". So the choice
comes down to what is best **for the project**.

The two are on a par for the TUI (Bubble Tea / ratatui), the Spotify client
(`zmb3/spotify` / `rspotify`) and distribution. They differ on:

- **Local embeddings**: the `fastembed` crate computes them in a few lines,
  with no Python and no remote service. In Go, ONNX through cgo.
- **Becoming a Spotify Connect device one day**: `librespot` is a Rust
  crate; in Go, impossible without rewriting it.
- **Neighborhood**: `spotifyd`, Omarchy-Spotify, fastpotify and librespot
  are Rust. The potential contributors in that ecosystem speak Rust.
- **Compiler**: Rust rejects wrong code where Go lets a `nil` or an ignored
  error through — a useful safety net when a good part of the code is
  written by an agent and reviewed by a human.

Go's advantages (goroutines, instant compilation, a small language) are
development comfort, not assets for the project.

## Decision

**Rust.** TUI with `ratatui`, Spotify API with `rspotify`, `tokio` runtime.

## Consequences

- The vectors of PoC step 2 are computed offline with `fastembed`.
- Embedding playback through `librespot` remains an open option, with no
  rewrite.
- The card format is not dictated by the language, but TOML is first class
  there (`serde` + `toml`) whereas `serde_yaml` has not been maintained by
  its author since 2024 (forks to be assessed). To weigh in the format
  choice ([design/catalog.md](../design/catalog.md)).
- Build in a container (everything is dockerized on Joel's machine), the
  binary runs on the host.
