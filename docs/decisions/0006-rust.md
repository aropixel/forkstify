# 0006 — L'application est écrite en Rust

**Date** : 2026-08-30 · **Statut** : acceptée

## Contexte

Une TUI clavier d'abord et un binaire unique distribuable sur Linux
désignaient deux candidats, Go et Rust. Joel a écarté d'emblée l'argument de
la facilité d'apprentissage : « si Rust est mieux, on prend Rust, c'est moi
qui m'adapterai ». Le choix se fait donc sur ce qui est le mieux **pour le
projet**.

Les deux se valent sur la TUI (Bubble Tea / ratatui), le client Spotify
(`zmb3/spotify` / `rspotify`) et la distribution. Ils se distinguent sur :

- **Embeddings en local** : la crate `fastembed` les calcule en quelques
  lignes, sans Python ni service distant. En Go, ONNX via cgo.
- **Devenir un jour un appareil Spotify Connect soi-même** : `librespot` est
  une crate Rust ; en Go, impossible sans réécrire.
- **Voisinage** : `spotifyd`, Omarchy-Spotify, fastpotify, librespot sont en
  Rust. Les contributeurs potentiels de cet écosystème parlent Rust.
- **Compilateur** : Rust refuse un code faux là où Go laisse passer un `nil`
  ou une erreur ignorée — un filet utile quand une bonne partie du code est
  écrite par un agent et relue par un humain.

Les avantages de Go (goroutines, compilation instantanée, langage petit)
sont du confort de développement, pas des atouts pour le projet.

## Décision

**Rust.** TUI avec `ratatui`, API Spotify avec `rspotify`, runtime `tokio`.

## Conséquences

- Les vecteurs de l'étape 2 du PoC se calculent hors-ligne avec `fastembed`.
- Embarquer la lecture via `librespot` reste une option ouverte, sans
  réécriture.
- Le format des fiches n'est pas dicté par le langage, mais TOML y est de
  première classe (`serde` + `toml`) alors que `serde_yaml` n'est plus
  maintenu par son auteur depuis 2024 (forks à évaluer). À peser dans le
  choix du format ([conception/catalogue.md](../conception/catalogue.md)).
- Build dans un conteneur (tout est dockerisé sur la machine de Joel), le
  binaire s'exécute sur l'hôte.
